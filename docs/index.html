DRAKE
Dynamic Runtime Adaptive Kernel Engine

A from-scratch compiler for LLM decode inference: shape-specialized operator fusion where the kernel-dispatch decision is compiled to real LLVM IR and JIT-executed — profiling the shapes a workload actually visits instead of committing to one schedule ahead of time.

The problem

Decode breaks the one-schedule assumption

Ahead-of-time inference compilers — TVM, XLA, TensorRT, torch.compile — pick one fusion plan and one kernel schedule per shape, decided once at compile time. That's fine for vision models with fixed input sizes.

Autoregressive decode

Every token, the same graph runs again with a seq_len — and a KV cache — one step larger. A server spends its whole life sliding along that curve, never sitting at one point.

Why one schedule loses

The plan that's optimal at token 16 — everything register-resident, no tiling — is not the plan you want at token 8,000, which must tile against shared memory / L2.

DRAKE's premise: don't pick one schedule. Profile the shapes you actually see, bucket them, and fuse + specialize lazily — per bucket, the first time each is hit.

The approach

Profile → bucket → specialize → JIT-dispatch

One decode step flows through a real compiler pipeline. The bucket-classification decision that gates every kernel is itself compiled to native code, so it doesn't cost an interpreted branch on the per-token hot path.

KV-cache-aware fusion

The one novel pattern collapses kv_cache_update → attn_qk → attn_softmax → attn_av into a single node, so the freshly written K/V for a token is consumed by attention without an intervening HBM round-trip — the same idea behind FlashDecoding and paged-attention kernels.

; the dispatch decision, compiled to LLVM IR
define i32 @drake_dispatch(i32 %seq_len, i32 %batch) {
entry:
  %.4 = icmp sge i32 %seq_len, 128
  %.5 = zext i1 %.4 to i32
  %.7 = icmp sge i32 %seq_len, 1024
  ...
  ret i32 %bucket_id
}

What's inside

A real pass pipeline

Each piece is independently tested — not a mock. Fusion, DCE and CSE are all proven semantics-preserving against the numpy executor.

Operator fusion

Greedy + cost-optimal DP

Longest-pattern-first for construction, plus a DP that provably maximizes analytic HBM-traffic saved for a concrete shape.

LLVM codegen

JIT dispatch

Bucket classifier lowered to LLVM IR via llvmlite, JIT-compiled, called through ctypes. Verified against a Python reference over a dense grid.

Specialization

Shape buckets

Buckets (seq_len, batch) and picks a kernel variant per fused op — vector vs. tiled attention, tile size, batch blocking.

Analysis

IR verifier

Single-assignment, def-before-use, output reachability, parameters vs. dangling refs — the safety net every other pass relies on.

Cleanup

DCE + CSE

Dead-code elimination and common-subexpression elimination, both wired into the engine build and re-verified after they run.

Scale & tooling

Multi-layer + DOT

Stack N transformer layers with independent KV caches; export any graph to Graphviz with Graph.to_dot().

Try it

Runs locally in a plain virtualenv

No GPU, no external services, no network calls — the whole pipeline is self-contained.

Honest scope

What's real, and what's a stand-in

Real and load-bearing: the IR, the fusion legality & connectivity check, the analytic traffic cost model, the shape-bucket specializer, and the LLVM codegen — genuinely generated, verified, JIT-compiled, and executed. Not a mock.

Stand-in, by design: the execution backend runs on numpy/CPU so the pipeline runs end-to-end without a GPU. It validates correctness — fusion never changes results — not GPU wall-clock, since CPU/numpy has no HBM-bandwidth bottleneck to relieve. Swapping it for a Triton or CUTLASS backend, without touching the IR or passes, is the natural next step toward measured GPU numbers.

No claim here is dressed up as more than it is. That distinction is deliberate.
